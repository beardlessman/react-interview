# State Managers Exam

Typical questions with short answers.

---

## General concepts

### What is state in a frontend application?

Data the UI depends on: user input, API responses, UI flags (modals, tabs), caches. State changes over time; when it changes, the UI should reflect the new data.

### How does local state differ from global state?

- Local — inside a component (`useState`, `useReducer`): form fields, hover, open/closed dropdown.
- Global — shared across many components via a store/Context: session, cart, theme, entity cache.

Rule: keep state as close as possible to where it is used; lift it into a store only when multiple tree branches truly need it.

### When do you need a dedicated store vs `useState` / Context?

A store helps with: complex shared state, frequent updates from many places, predictable transitions, middleware/devtools, normalized entities.  
`useState` — local UI. Context — rarely changing “config” (theme, locale, auth user). Using Context as a store for high-churn state causes extra re-renders.

### What are Flux and unidirectional data flow?

Pattern: View → Action → Dispatcher/Store → Store update → View. Data flows one way; the View does not mutate the store directly. Redux is a Flux evolution (single store, pure reducers).

### What is immutability and why does state management care?

Do not mutate objects/arrays in place — create new references. Benefits: predictable updates, cheap `===` checks, time-travel/devtools, safer sharing. Required in Redux/RTK; MobX allows mutations inside `action`.

### What are selectors?

Functions that read/derive data from the store: `state => state.user.name`. Memoized ones (`reselect`, `createSelector`) recompute only when their input slices change — fewer unnecessary re-renders.

### What is middleware in a store context?

A layer between `dispatch` and the reducer: logging, crash reporting, async (thunk), routing. In Redux: `(store) => (next) => (action) => ...`. RTK already wires `redux-thunk` and DevTools.

### How does a thunk differ from a saga (briefly)?

- Thunk — a function the middleware calls with `dispatch`/`getState`; good for simple async (fetch → dispatch).
- Saga — generators + effects (`call`, `put`, `take`); better for complex flows: cancellation, debounce, races, background jobs. Most apps are fine with thunk / `createAsyncThunk` / RTK Query.

### What is normalized state?

Storing collections as `{ ids: [], entities: { [id]: item } }` instead of deep nested trees. Pros: no duplication, O(1) update by id, simpler selectors. In RTK — `createEntityAdapter`.

### What side-effect strategies are used with a store?

1. In the component (`useEffect`) — simple, but scattered.  
2. Thunk / `createAsyncThunk` — next to store logic.  
3. Saga / listener middleware — complex scenarios.  
4. RTK Query / React Query — server data cache and requests built-in.  
Choice depends on complexity and server vs client state.

### How does client state differ from server state?

- Client: UI, form drafts, selected filters — client is the source of truth.  
- Server: API data — a cache with stale/refetch, errors, pagination.  
For server state, RTK Query / TanStack Query is often better than hand-rolled Redux.

### What is a single source of truth?

One canonical data source for a domain (store or query cache). Avoids desynced copies across components. It does not mean “everything in one giant object” — local UI state can live separately.

## Redux

### What is Redux and what are its principles?

A predictable state-container library. Principles: a single store; state is read-only (change via `dispatch`); updates go through pure reducers `(state, action) => newState`.

### What parts make up classic Redux?

Store, actions (plain objects with `type`), reducers, `dispatch`, `subscribe`, often `combineReducers`, middleware, `bindActionCreators`. UI connects via `react-redux`.

### What is the store? How do you create it in classic Redux?

An object with `getState`, `dispatch`, `subscribe`, `replaceReducer`.  
`createStore(reducer, preloadedState?, enhancer?)` — modern code prefers RTK `configureStore`.

### What is an action?

A plain object describing “what happened”: at least `{ type: 'todos/add' }`, often with `payload`. Action creators are functions that return actions. In RTK, types are generated by `createSlice`.

### What is a reducer?

A pure function `(state, action) => nextState`. No side effects, no mutations (in classic Redux), deterministic. For an unknown action it returns the previous `state`.

### What does `dispatch` do?

The only way to trigger a change: `store.dispatch(action)`. The action goes through middleware → root reducer → new state → subscribers notified → re-render.

### What is `subscribe` for?

Subscribe to any store change: `const unsub = store.subscribe(listener)`. In React you rarely call it manually — `react-redux` does that.

### How do `combineReducers` and state shape relate?

`combineReducers({ users, posts })` yields state shaped `{ users, posts }`. Each slice reducer owns its key. The root reducer forwards the action to all children.

### How does `connect` differ from `useSelector` / `useDispatch`?

- `connect(mapState, mapDispatch)(Component)` — HOC, class/legacy style.  
- Hooks — in function components: `useSelector` reads a slice, `useDispatch` returns `dispatch`.  
Modern default is hooks; `connect` appears in legacy code.

### How does `useSelector` decide whether to re-render?

By default it uses strict `===` on the selector result. Returning a new object/array every time causes extra renders. Fix: select stable primitives/references or memoize the selector; optionally pass a custom `equalityFn`.

### What is an action creator and why the payload convention?

A function `addTodo(text) => ({ type: 'ADD', payload: text })`. An FSA-like convention (`payload`, `error`, `meta`) helps middleware and RTK. With `createSlice`, action creators are generated automatically.

### Can a reducer do async / API calls?

No — reducers must be pure and synchronous. Async belongs in middleware (thunk), listeners, RTK Query, or UI effects that later `dispatch` sync actions.

### What are Redux DevTools and why time-travel?

An extension: action log, state diff, “rewind” to past states. Works because of immutability and pure reducers. RTK enables it via `configureStore` by default in development.

### How do you type Redux with TypeScript (briefly)?

`RootState` and `AppDispatch` types from the store; `useAppSelector` / `useAppDispatch` hooks; in RTK — inferred types from `createSlice` / `createAsyncThunk`. Avoid `any` on `payload`.

## Redux Toolkit

### What is Redux Toolkit (RTK) and what problem does it solve?

The official way to write Redux: less boilerplate, Immer built-in, sensible defaults (`configureStore`), built-in thunk, simpler slices and async. The Redux team’s recommendation over hand-rolled classic setup.

### What does `configureStore` do?

Creates a store with sensible defaults: combines reducers, adds thunk and DevTools, checks serializability/immutability in dev. Replaces `createStore` + manual `applyMiddleware`.

### What is `createSlice`?

API: slice name, `initialState`, a `reducers` object (and optional `extraReducers`). Generates action creators and action types. Inside reducers you may “mutate” a draft — Immer produces the immutable result.

### How does Immer work in RTK?

Reducers receive a Proxy draft. You can write `state.value = 1` or `state.list.push(x)`. Immer records changes and returns a new state. Do not mix mutating the draft and `return`ing a new object in one reducer without knowing Immer’s rules.

### What is `createAsyncThunk`?

A factory for async action creators: pending / fulfilled / rejected. The `payloadCreator` does the request; results are handled in `extraReducers` or `builder.addCase`. Removes hand-written triples of action types for typical fetch cycles.

### How do you handle a thunk result in a slice?

Via `extraReducers: (builder) => { builder.addCase(fetchUser.pending, ...).addCase(fetchUser.fulfilled, ...) }` or map notation. Update `status`, `error`, and data in state.

### What is `createEntityAdapter`?

A helper for normalized collections: `ids` + `entities`, CRUD reducers (`addOne`, `setAll`, `updateOne`, `removeOne`), selectors (`selectAll`, `selectById`). Handy for lists with frequent point updates.

### What is RTK Query?

RTK’s data-fetching/caching module: define `createApi` + endpoints (`query`/`mutation`), get hooks (`useGetPostsQuery`). Cache, request deduping, tag invalidation, refetch — without hand-written thunks for CRUD APIs.

### How does `query` differ from `mutation` in RTK Query?

- `query` — reads (GET-like), cached by arguments.  
- `mutation` — writes (POST/PUT/DELETE); after success you usually `invalidateTags` so related queries refetch.

### What is tag-based invalidation in RTK Query?

Endpoints tag data (`providesTags` / `invalidatesTags`). A mutation invalidates a tag → related queries refetch. Simpler than manually syncing the cache.

### Do you still need redux-thunk separately with RTK?

Usually no: `configureStore` already adds thunk middleware. Add other middleware (saga, custom) via `middleware: (getDefault) => getDefault().concat(...)`.

### What is listener middleware in RTK?

`createListenerMiddleware` — react to actions (a lighter alternative to some saga scenarios): side effects, debounce, sync, without generators. Useful for “when action X — do Y”.

### How do you organize slices in a large app?

By domain/feature: `userSlice`, `cartSlice`, feature folders. Root — `configureStore({ reducer: { user, cart, api: api.reducer } })`. Avoid a god-slice “for everything”.

### How do RTK patterns differ from “classic” Redux code?

Fewer hand-written constants/action creators; Immer instead of manual spreads; `configureStore` instead of DIY assembly; async via `createAsyncThunk`/RTK Query; fewer files per feature. The semantics (actions → reducers → store) stay the same.

## MobX

### What is MobX?

A reactive state library: mark data as `observable`; reactions/components automatically track reads and update on changes. Mutations usually go through `action`. Less boilerplate than Redux.

### What is `observable`?

Data the MobX runtime tracks. Reading it inside `observer`/`computed`/`reaction` registers a dependency; writing schedules dependent reactions to re-run.

### What is an `action` in MobX?

A function that changes observables. Batches mutations into one transaction (fewer intermediate re-renders). In strict mode you must not change state outside an `action`.

### What is `computed`?

A derived value from observables (like a memoized selector). Cached and recomputed only when dependencies change. Example: `get fullName() { return this.first + ' ' + this.last }`.

### How do `reaction` / `autorun` / `when` differ?

- `autorun` — runs immediately and again whenever tracked dependencies change.  
- `reaction` — separate tracking function and effect; the effect runs only when the selected value changes.  
- `when` — once, when a predicate becomes true.  
For UI, `observer` is usually enough; reactions are for side effects outside React.

### What does `observer` (mobx-react) do?

A HOC/wrapper: during render it tracks read observables and subscribes the component. A dependency change → re-render only that `observer` component (with good granularity).

### What are `makeAutoObservable` / `makeObservable`?

- `makeObservable` — explicit field annotations (`observable`, `action`, `computed`).  
- `makeAutoObservable` — infers annotations (fields → observable, getters → computed, methods → action). Fast start; override specifics as needed.

### What is MobX strict mode (`enforceActions`)?

A mode where state may only change inside an `action` (often `enforceActions: 'observed'` or `'always'`). Catches accidental mutations outside transactions and makes change flow explicit.

### How does MobX track dependencies (reactivity tracking)?

While a reaction/`observer` render runs, MobX collects read observable fields. Subscriptions are fine-grained: changing an unread field does not update the component. Avoid carelessly destructuring observables “before” tracking.

### Can you mutate state in MobX?

Yes — that is idiomatic inside `action` (unlike Redux). MobX notifies subscribers. Outside React you still should not scatter hidden mutations without actions.

### How are stores structured in MobX?

Often class-stores or object-stores per domain plus a root store / React Context for DI. Not necessarily one global object; clear boundaries and leaf `observer` components matter.

### MobX 6 — what matters vs older versions?

Decorators are optional: `makeObservable` / `makeAutoObservable`. Proxy mode is the default. Cleaner TypeScript without experimental decorators. “Class + makeAutoObservable” is the typical modern style.

## Comparison and practice

### Redux vs MobX: what is the main difference in approach?

Redux — explicit unidirectional flow, immutable state, all changes via actions/reducers (easy to audit).  
MobX — reactive mutations, less ceremony, automatic dependencies.  
Redux is more predictable in large teams; MobX is faster to write for rich object graphs.

### When choose Redux/RTK vs MobX?

- RTK: you need a strict audit trail, DevTools/time-travel, a large team, lots of async/server cache (RTK Query).  
- MobX: rich domain model, frequent local mutations, less boilerplate desired.  
- Zustand: simple global state without Redux ceremony — a solid lightweight option.

### What is Zustand and how does it relate to Redux/RTK?

A minimal hook-based store: `create((set, get) => ({ ... }))`. No mandatory actions/reducers; write immutably or with Immer middleware. Selector and slice patterns feel like a simplified Redux, often without a Provider (optional context exists).

### What are common Redux performance pitfalls?

Overly broad `useSelector` / returning new objects; huge state without normalization; heavy work without memoization; dispatching tiny updates too often; abusing Context instead of selectors. Fixes: precise selectors, `createSelector`, entity adapter, RTK Query for server data.

### What are common MobX performance pitfalls?

Large `observer` components that read too much; destructuring observables and losing tracking; reactions without dispose; excessive `autorun`. Prefer small `observer` leaves and `computed` for derived data.

### How do you test a Redux store / slices?

Pure reducers — unit tests `(state, action) => next`. Thunks — mock the API and assert the dispatch sequence. Integration — `configureStore` + `render` with Provider, assert UI. RTK means less test boilerplate.

### How do you test MobX stores?

Create a store, call actions, assert fields and `computed`. For React — render under `observer`, mutate the store, wait for UI updates. For reactions — assert the effect and always dispose in afterEach.

### How should you mix local UI state and a global store?

Store — domain data and anything shared across routes/features. Component — ephemeral UI (modal open, input value before submit). Do not push every keystroke into Redux “just in case”.

### How do you organize side effects in practice?

CRUD API → RTK Query / TanStack Query. Simple request + write to client store → `createAsyncThunk`. Chains/cancellation/background work → listener middleware or saga. UI-only effects → `useEffect`. Do not duplicate the same fetch in three places.

### Do you still need Redux if you already have React Query / RTK Query?

Not always. Server state is covered by the query library; Redux/Zustand/MobX handle complex client state. A common hybrid: RTK Query + a thin client slice (or Zustand) for UI/workflow.

### How do you avoid prop drilling without a “heavy” store?

Composition, colocating components, Context for rare data, a lightweight Zustand/MobX store per feature. Global Redux does not have to solve every two-level prop pass.

### What are signs of an overgrown store (when to simplify)?

Hand-duplicated server cache; actions only to tunnel props; half the state never shared; tests/onboarding hurt more than features. Then move server state to Query, keep local UI in components, leave the store for truly shared domain data.
