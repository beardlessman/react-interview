# Критические баги

1. Интервал не очищается и не вызывается сразу. setInterval в эффекте с [] создаёт таймер и не возвращает clearInterval. После размонтирования таймер продолжает вызывать setUsers. В Strict Mode эффект ставится дважды, и интервалы накапливаются. Сам setInterval первый раз срабатывает только через 5 секунд, хотя комментарий говорит про загрузку при монтировании — список пустой, пока не пройдёт первый тик.

2. Поиск не фильтрует список. filter читается внутри useMemo, но в зависимостях только users. Пока массив пользователей не сменится, мемо возвращает старый результат, и ввод в поле ничего не меняет в списке.

3. key={Math.random()}. На каждом рендере у каждой строки новый ключ. React считает все 1000 элементов новыми, сносит старые DOM-узлы и создаёт их заново. Теряется идентичность строки, а любой локальный state внутри строки сбрасывается.

4. Счётчик кликов закрывается над устаревшим state. setClickCount(clickCount + 1) берёт значение из текущего рендера. Пока тяжёлый рендер не закончился, несколько кликов могут прибавить одно и то же число. Нужен функциональный апдейт: setClickCount((count) => count + 1).

# Оптимизации

1. Критическая проблема производительности: Дебаунсинг ввода (Debouncing)

Даже с учетом того, что вы добавили filter в зависимости useMemo, при каждом нажатии клавиши в инпуте (onChange) состояние filter обновляется мгновенно.
• В чем проблема: Пользователь быстро вводит слово из 10 букв — компонент перерендеривается 10 раз, и 10 раз запускается «тяжелая» фильтрация списка из 1000 элементов. Интерфейс будет заметно фризиться при вводе.
• Решение: Разделить стейт инпута (быстрый) и стейт для фильтрации (медленный, через debounce на 300мс), либо дебаунсить само вычисление/запрос.

2. Избыточные ререндеры элементов списка (Мемоизация компонентов)

Сейчас при клике на любого пользователя увеличивается clickCount.
• В чем проблема: Изменение clickCount вызывает ререндер всего компонента UsersDashboard. Так как элементы списка (те самые 1000 div) не мемоизированы, React будет заново рендерить все 1000 карточек пользователей при каждом одиночном клике, даже если их данные не изменились.
• Решение: Вынести карточку пользователя в отдельный компонент (например, UserRow) и обернуть его в React.memo.

3. Лишние сетевые запросы (Оптимизация useEffect для логов)

Вы исправили баг со stale closure, используя setClickCount(count => count + 1). Но посмотрите на useEffect, который отправляет логи:
• В чем проблема: Он реагирует на каждое изменение clickCount. Если пользователь бешено кликает, приложение будет спамить сетевыми запросами navigator.sendBeacon на каждый клик.
• Решение: Для аналитики кликов лучше убрать этот useEffect вообще, а отправку логов делать прямо внутри обработчика handleUserClick (возможно, тоже с дебаунсом или троттлингом), либо собирать клики в буфер и отправлять пачкой.

# Тонкости

1. Утечка памяти в дебаунсе кликов при размонтировании (Memory Leak)

Ваш handleUserClick использует setTimeout и сохраняет его ID в logTimerRef.current.
• В чем проблема: Если пользователь кликнет по карточке, запустится таймер на 300 мс, а затем пользователь сразу уйдет с этой страницы (компонент размонтируется). Таймер останется висеть в памяти браузера. Когда он сработает, он попытается выполнить коллбэк, который обращается к pendingClicksRef.current и вызывает navigator.sendBeacon. В лучшем случае это просто лишний фоновый запрос, в худшем (если внутри коллбэка появится апдейт стейта) — предупреждение в консоли или утечка памяти.
• Решение: Очищать logTimerRef.current в useEffect при размонтировании компонента.

```
tsx
useEffect(() => {
  return () => {
    if (logTimerRef.current) clearTimeout(logTimerRef.current);
  };
}, []);
```


2. Проблема UI/UX: Гонка условий при «тяжелом» поиске (Race Condition / UI Blocking)

Вы оптимизировали количество запусков фильтрации с помощью дебаунса в 300 мс.
• В чем проблема: Метод Array.prototype.filter вместе с циклом while внутри useMemo — это синхронная блокирующая операция. На 1000 элементов с задержкой 0.5 мс это займет ~500 мс «чистого» времени блокировки главного потока (Main Thread). Когда дебаунс наконец сработает и запишет новое значение в filter, интерфейс полностью «замрет» на полсекунды. Если пользователь продолжит вводить текст в этот момент, инпут залагает.
• Решение: В реальном мире такие тяжелые вычисления уносят на бэкенд или в Web Worker. Но если нужно решить это строго на фронтенде в рамках React 18+, правильным ответом будет использование useTransition. Мы оборачиваем setFilter в startTransition, помечая это обновление как низкоприоритетное. Это позволит инпуту оставаться отзывчивым, даже когда идет тяжелый рендеринг списка.


3. Тонкий нюанс: Использование useCallback без зависимостей

Ваш handleUserClick не имеет зависимостей ([]). Это корректно, потому что вы используете функциональный апдейт стейта setClickCount((count) => count + 1) и мутируете рефы, которые стабильны между рендерами.
• Интервьюер может спросить: «Безопасно ли это?» Ваш ответ должен быть: «Да, так как рефы и функция-сеттер гарантируют стабильность ссылок, но если в будущем внутри коллбэка понадобятся другие пропсы или стейт, массив зависимостей придется обновить».
